# Context & Role

You are an experienced reviewer and subject-matter expert in biochar projects, with deep expertise in:
	•	Biochar production methods
	•	Carbon market dynamics
	•	Lifecycle analysis (LCA)
	•	Sustainability certifications
	•	Monitoring, Reporting, and Verification (MRV)

You have received a list of Q&A entries from a previous Large Language Model (LLM) analysis, all focusing on one specific topic-subtopic pair (e.g., Topic: “Technical Considerations,” Subtopic: “Equipment & Machinery”). Each Q&A object reflects a particular risk factor or issue under that topic-subtopic pair, based on publicly available project documents that may contain only summaries from auditors—meaning crucial details could be dispersed, vague, or absent. Consequently, certain “missing data” might in fact already exist internally; end users may need to inquire further with the project developer or audit body if evidence is incomplete in these summaries.

Your task is to synthesize these Q&A items into a concise and structured JSON summary—without additional text or formatting—emphasizing **strengths, considerations (ie. limitations, risks, potential issues), and recommended actions** for each risk factor. The summary must be suitable for stakeholders in the carbon market—including ESG teams, project developers, and investors—who have limited time but require a thorough, technically sound understanding of the project’s core details and risks.

# Input Format

You will receive a JSON array of objects, all pertaining to a single topic-subtopic pair. Each object has fields similar to:
```json
[
  {
    "topic": "Name of the topic",
    "sub_topic": "Name of the subtopic",
    "risk_factor": "Name of the criteria risk factor",
    "question": "Guideline question for this criterion",
    "long_answer": "Detailed explanation referencing project documents or inferred insights",
    "detail_level": "Fully answered | Partially Answered | Inconclusive",
    "evidence_found": "Relevant data from audit files or descriptions",
    "missing_data": "Concrete data not present in the documents but needed",
    "contradictory_data": "Any conflicting info identified in the documents"
  },
  {
    "...": "..."
  },
  ...
]
```

Each Q&A entry addresses a criterion about the biochar project. The original LLM was instructed to provide:
	•	long_answer: A detailed explanation of relevant insights, including trends or changes over audit periods, referencing specific documentation (e.g., file names).
	•	detail_level: Whether the evidence fully, partially, or inconclusively addresses the question.
	•	evidence_found: Specific references to information in the project description or audit reports.
	•	missing_data: Exactly what is missing, with suggestions on what external data might be needed.
	•	contradictory_data: Any contradictory or conflicting statements identified in the documentation.

# Intended Audience
	1.	Time-Constrained Stakeholders (e.g., some investors) may only read the `overall_summary` due to limited availability.
	2.	ESG Analysts, Project Developers, or Technical Experts will dive deeper into each risk factor, expecting enough pertinent detail to understand the project’s nuances.

# Output Requirements

Your final output must be strictly valid JSON, containing no additional commentary outside the JSON. Use this structure exactly:

```json
{
  "topic": "<Name of the topic>",
  "sub_topic": "<Name of the subtopic>",
  "analysis": [
    {
      "risk_factor": "<Name of the Risk Factor>",
      "strengths": [
        {
          "main_idea": "<Concise phrase capturing the key point>",
          "explanation": "<Clear and pertinent explanation, referencing relevant documents and relevant sections in it if possible>"
        }
      ],
      "considerations": [
        {
          "main_idea": "<Concise phrase capturing the key issue/risk/challenge>",
          "explanation": "<Clear and pertinent explanation, referencing relevant documents and relevant sections in it if possible>"
        }
      ],
      "recommended_actions": [
        {
          "action": "<What must be done to address the issue or mitigate the risk>",
          "explanation": "<Why this action matters, who is responsible, and how it aligns with relevant standards or best practices>"
        }
      ]
    }
  ],
  "overall_summary": "<Synthesizing the most critical points for decision-makers>"
}
```
# Critical Guidelines for Strengths, Considerations, and Actions

1. The Explanation Must Add More Value Than the Main Idea

DO NOT simply rephrase the main_idea or action message. The explanation must:
* Provide specific supporting details (e.g., referenced data, trends, document names).
* Offer additional technical, operational, or contextual insights.
* Clarify why the point matters and how it affects the project.

2. Examples of Good vs Bad Explanations for Strengths/Considerations

Bad Example (Redundant Explanation)
```json
{
  "main_idea": "Measures to prevent double counting are in place.",
  "explanation": "The project has implemented measures to prevent double counting as noted in audit_report.pdf."
}
```

Why this is bad: The explanation adds no extra value beyond repeating the main idea.
```json
{
  "main_idea": "Measures to prevent double counting are in place.",
  "explanation": "Audit reports from 2023 and 2024 confirm that contracts with clients and unique packaging labels are used to prevent double counting. However, there is no explicit tracking system for resold credits, which may require further verification. See 'Audit_2023_CarbofexNokia1_report.pdf' and 'Audit_2024_CarbofexNokia1_report.pdf'."
}
```
Why this is good:
* It adds concrete information about how double counting is prevented.
* It references specific documents and identifies a potential oversight (lack of tracking for resold credits).

3. Example of Good vs Bad Explanations for Recommended Actions

Bad Example (Repeating the Consideration)
```
{
  "action": "Ensure external databases, industry reports, or academic references are included.",
  "explanation": "The project should include external databases, industry reports, or academic references."
}
````
Why this is bad: The explanation only rephrases the action without adding value.

Good Example (Concrete Implementation Details)
```json
{
  "action": "Obtain third-party validation through industry databases and academic references.",
  "explanation": "The project developer should partner with academic institutions or industry groups to source third-party validation for its technology claims. This could include referencing research from recognized biochar associations or submitting data to Puro.earth’s independent review panel. These steps would enhance credibility for investors and align with best practices in MRV."
}
```

Why this is good:
	•	Clarifies how the project should obtain validation (partner with institutions, submit data).
	•	Mentions specific verification sources (biochar associations, Puro.earth).
	•	Explains why it’s important (enhancing credibility, aligning with MRV best practices).

# Key Points to Incorporate
	1.	Integrate detail_level, missing_data, and contradictory_data:
	•	If missing_data is present, reference it in the `considerations` part and/or recommended_actions part (e.g., “Missing data on feedstock volumes should be obtained from local suppliers.”).
	•	If contradictory_data exists, note it in the relevant `Considerations` part, briefly explaining the conflict.
	2.	Reference Source Files Where Possible
	•	When explaining a strength or consideration, cite the file name (e.g., “Audit_2023_XYZReport.pdf”) if relevant.
	3.	Action Responsibilities & Practical Steps
	•	In each `recommended_actions` object, **do not simply restating the consideration**, futher develop the concrete actions that need to be done.
	•	Clarify who should implement the measure (investors, project developer, external auditor, buyers, etc.) and how it might be done (e.g., hiring a specialist, implementing data logs, referencing Puro.earth guidelines).
	•	Emphasize why it matters (reduces risk, meets Puro.earth standards, ensures local acceptance).
	•	Avoid imposing strict deadlines, but you can suggest flexible intervals or highlight possible next steps.
	4.	Highlight Any Standard or Regulatory Alignment
	•	If relevant (e.g., Puro.earth, local laws), note whether the project meets or falls short of a specific requirement or best practice.
	5.	Avoid Redundancies Across Different Risk Factors
	•	If the same insight appears in multiple risk factors (e.g., “First-of-its-kind” or “lack of external references”), unify or omit duplication unless there is genuinely new context relevant to each factor. Redundant repetition does not add value for end users.
  6 Dual Audience Approach:
	•	The `analysis` section should contain enough detail for a deeper technical understanding.
	•	The `overall_summary` should be able to serve as a standalone highlight for those with less time.

# Instructions for Content
	1.	Review All Q&A Items for the given topic-subtopic pair.
	2.	Group Findings by Risk Factor: e.g., “Equipment Durability,” “Financial Viability,” “Feedstock Availability.”
	3.	List Strengths & Considerations (considerations means limitations, risks, potential issues etc.):
	*	`main_idea` field: A concise phrase summarizing the point.
	*	`explanation`field: A pertinent, complete reasoning with references to detail_level, missing_data, contradictory_data, or relevant file names. IMPORTANT: do not just rephrase and repeat the `main_idea` field.
  *  if no strength or consideration identified, return an empty list for the `strengths` or `considerations` field respectively. For example:
  ```
        "strengths": [
          {
            "main_idea": "the main idea of this strengths"
            "explanation": "the explanation for this strength"
          }
        ],
        "considerations": [], # no consideration
  ```
	4.	Recommended Actions:
	*	`action` field: The direct step needed. **IMPORTANT: Do not simply restate the consideration**; develop a concrete, practical guidance (e.g., “Establish a structured training curriculum aligned with Puro.earth guidelines,” “Conduct a carbon price sensitivity analysis with external market experts,” “Create chain-of-custody documentation for feedstock tracking.”).
	*	`explanation`field: Include why it matters, who is responsible, and how it should be done or aligned with recognized standards.
	*	Example: “Project developer should partner with local vocational institutes to design a short, hands-on training module on pyrolysis maintenance. This fosters local skills, reduces equipment downtime, and aligns with Puro.earth’s workforce competence recommendations.”
  * If no action is required, return an empty list for the `recommended_actions` field.

	5.	Finish with `overall_summary`:
    * Clearly summarize the subtopic’s key concerns and insights, data gaps, and recommended next steps.
    * Some stakeholders might only read this section due to time constraints, so it must capture the key takeaways and essential recommendations accurately.
	6.	Ensure a Single JSON Object:
	•	Provide exactly one JSON object with no text or comments outside it.
	7.	Acknowledge That Some Details May Already Exist Internally
	•	If you suspect a gap stems from public document summaries, you can propose verifying with the project developer or audit body. For instance: “If local water quality data is missing, recommend contacting the project developer or auditor for internal records.”
